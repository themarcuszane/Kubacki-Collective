# Kubacki Collective security review — November 25, 2026

Identity: **Kubacki Collective**, **By TeamDryBox LLC**. Public site: <https://kubackicollective.com>. Repository: [themarcuszane/Kubacki-Collective](https://github.com/themarcuszane/Kubacki-Collective).

Reviewed source: [`f96ef62045fad4b4b6c4bb1821120e543b91c3ce`](https://github.com/themarcuszane/Kubacki-Collective/tree/f96ef62045fad4b4b6c4bb1821120e543b91c3ce), verified against remote main. Review date uses America/Boise; captured HTTP timestamps fall on November 26 UTC.

## Assessment

**Action is required.** The most material production issue is a publicly readable S3 website origin reached over HTTP, bypassing the CloudFront/WAF boundary. Browser security headers and release controls need hardening. The repository has vulnerable dependencies, unprotected main, and failing CI.

There is **no confirmed critical exploit of the live static site** in this review. The npm scanner's critical classifications concern repository packages and their advisory prerequisites; they are not proof of exploitable Next.js servers on S3. No verified credentials were found in scanned history or published text artifacts. This is a point-in-time review, not a guarantee that vulnerabilities or past compromise do not exist.

The unrelated **CareerOS scaffold is not the public collective site**. Checked production auth/workspace paths return 404. Its server-side risks are identified separately and must not be attributed to the current static deployment.

## Scope and method

- Read-only HTTP checks of public routes, HTTPS redirects, sensitive-file paths, source maps, CORS preflight, origin access, TLS, and response headers; bounded requests, no load testing or write/exploit attempts.
- AWS configuration review: identified CloudFront distribution, its S3 origin and complete 266-object inventory, bucket access/ownership/encryption/recovery settings, and attached WAF rules.
- GitHub review: source at the recorded commit, main protections/rulesets, security settings, alert metadata, workflow token defaults, recent CI runs, and failed-run evidence.
- `npm audit --json` and `npm audit --omit=dev --json` against the committed lockfile, with current advisory data.
- Gitleaks 8.30.1, downloaded from its official release and verified against release SHA-256 checksums: reachable local Git history and all 248 published text artifacts (2,903,320 bytes). The published-artifact scan produced one false positive, triaged below.
- Focused source review of content loading, MDX, authentication/session guards, profile writes, SQL ownership policies, browser sinks, public forms, and deployment boundaries. Local reproduction used the existing public ARCHITECTURE.md file, not private data.
- Existing unit tests and TypeScript checks. No application, AWS, DNS, database, GitHub protection, or production deployment settings were changed by the review. Publication adds review documents/issues only.

Sanitized evidence is in [evidence/2026-11-25](evidence/2026-11-25/). [Verification commands](2026-11-25-verification.md) support follow-up work. Account identifiers, credentials, raw application/source-map bodies, and temporary paths are excluded from published evidence.

## SEC-01 — Replace public HTTP origin with private OAC access

**Evidence:** CloudFront uses `kubackicollective.com.s3-website-us-west-2.amazonaws.com` as a custom origin with `OriginProtocolPolicy: http-only`, no OAC, and no custom authentication headers. The bucket policy permits anonymous `s3:GetObject` on every object. All four bucket public-access-block controls are false; account-level public-access blocking is not configured. Bucket policy status is public.

An anonymous HTTP request to the website origin returns 200 and the same SHA-256 homepage body as the public site. An anonymous, certificate-valid path-style S3 HTTPS request also returns the homepage. Direct reads bypass the WAF, edge restrictions, and future CloudFront header controls. The CloudFront-to-origin connection is plaintext, despite HTTPS at the viewer. No anonymous write permission was found in the bucket policy/ACL; write attempts were not performed. Public access to intended public content alone is not a private-data breach.

**Remediation and acceptance:**

- Use a regular S3 REST origin, OAC, and always-signed HTTPS requests; restrict object reads to the intended distribution.
- Reproduce website directory-index and redirect behavior in the edge routing before switching origins. A REST origin does not automatically provide S3 website routing.
- Validate `/`, `/collective`, `/collective/`, chapter/journal details, assets, and genuine missing URLs on a preview. Preserve collective/company branding.
- After the new origin works, enable all four bucket public-access-block controls and verify anonymous origin reads fail while the site works. Do not block public reads before replacing the website origin; that would interrupt the current site.
- Keep a tested rollback plan and record the final configuration in GitHub.

[AWS documents OAC and the website-endpoint limitation](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html).

## SEC-02 — Add CloudFront browser security headers

**Evidence:** `/`, `/collective/`, `/chapters/`, `/journal/`, and `/start/` lack `Strict-Transport-Security`, `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, and `Permissions-Policy`. The distribution has no response-headers policy. HTTP redirects to HTTPS, but HSTS is absent. This is defense in depth; no working XSS, clickjacking-based account compromise, or credential theft was demonstrated.

**Remediation and acceptance:**

- Attach a reviewed CloudFront response-headers policy, including `nosniff`, suitable referrer/frame restrictions, and a minimal permissions policy.
- Inventory the inline Next.js scripts/styles; stage CSP in report-only mode before enforcing a compatible static-site policy. Include restrictions for `object-src`, `base-uri`, `frame-ancestors`, and `form-action`. Use appropriate script hashes or another reviewed static-site strategy; a strict policy applied blindly can break hydration.
- Stage HSTS; add `includeSubDomains` or preload only after verifying all affected hostnames.
- Check root, directory routes, assets, errors, branding, and browser console after rollout. Headers in Next.js server configuration alone do not configure S3/CloudFront.

[AWS response-header policy documentation](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/understanding-response-headers-policies.html).

## SEC-03 — Update vulnerable locked dependencies

**Evidence:** The complete scan reports **31 affected package entries: 4 critical, 12 high, 13 moderate, 2 low**. The production-dependency-only scan reports **9 entries: 1 critical, 6 high, 2 moderate**. These counts include transitive/aggregate package findings and are not distinct CVE counts. All affected entries report a fix available at scan time.

Locked versions include Next.js 16.1.6, Vitest/@vitest/ui 3.2.4, Vite 7.3.1, and PostCSS 8.5.6. Critical entries are Next.js, Vitest, @vitest/ui, and tinypool. See the full and production-only JSON evidence for every package, advisory URL, range, and proposed fix.

**Reachability:** S3 serves static artifacts; checked `/sign-in`, `/sign-in/`, `/sign-up/`, `/dashboard/`, and `/auth/callback` return 404. Server Actions, image-optimization services, Node server middleware, and dev/test servers are not established as live production endpoints. Many Next.js advisories require those runtimes or specific features. An exposed Vitest UI or later deployment of the server scaffold would change the risk materially. A `dependencies` classification in npm does not mean the entire package ships in static browser output.

**Remediation and acceptance:**

- Update direct/transitive dependencies with a regenerated committed lockfile; align Next.js-related packages and a supported Node LTS runtime.
- Check current patch ranges and advisory prerequisites rather than assuming an older patch resolves all later advisories. Avoid an unreviewed forced upgrade.
- Run complete/production audits, unit tests, type checks, lint, the intended static build, and meaningful browser checks; document remaining advisories and justified exceptions with owners/expiry.
- Keep development/test UI servers private and verify release contents contain only the collective public site.

Examples: [Next.js Server Actions origin validation advisory](https://github.com/advisories/GHSA-mq59-m269-xvcx), [Vitest UI file-read/execution advisory](https://github.com/advisories/GHSA-5xrq-8626-4rwp). These examples do not replace the full evidence.

## SEC-04 — Protect main and release integrity

**Evidence:** The branch-protection API explicitly reports `Branch not protected`; repository rulesets are `[]`. A writer can bypass CI/review or rewrite release history. This is a missing control, not evidence of compromise.

**Remediation and acceptance:** Add branch protection/rulesets requiring PRs and meaningful passing checks, block deletion/force pushes, and explicitly decide administrator bypass. Establish passing public-site CI before requiring it. Choose an achievable review requirement for the actual maintainer count, avoiding a sole-maintainer approval deadlock. Verify the resulting configuration without force-push tests on main.

[GitHub protected-branch documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

## SEC-05 — Restore CI and continuous security checks

**Evidence:** The [reviewed commit's CI run](https://github.com/themarcuszane/Kubacki-Collective/actions/runs/41276495298) failed E2E testing because global Supabase middleware required absent project URL/key values; Build was skipped. The latest five inspected main push runs failed. Unit testing passed. Dependabot security updates are disabled; the alerts endpoint explicitly reports alerts disabled. Code scanning reports no analysis. The sole workflow has no dependency audit, credential scan, or source-security job, and references Actions by mutable major-version tags.

CI uses Node 20. The [official Node schedule](https://raw.githubusercontent.com/nodejs/Release/main/schedule.json) records end of support on April 30, 2026, before this review. Positives: default Actions token permissions are read-only and PR self-approval is disabled.

**Remediation and acceptance:**

- Make public-site tests/builds independent of unrelated CareerOS/Supabase configuration, on a supported Node LTS.
- Enable Dependabot alerts/security updates and maintain dependency update configuration. Add proportionate dependency, source, and secret checks.
- Specify least-privilege workflow permissions, pin Actions to reviewed commit SHAs, and maintain those pins. Keep production secrets out of untrusted/fork PR execution.
- Verify a complete successful public-site CI run, including release build, before making checks required on main. Do not solve missing test configuration by exposing production credentials.

[Dependabot security-update documentation](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-security-updates).

## SEC-06 — Make static releases reproducible and exclude unintended artifacts

**Evidence:** The complete bucket inventory contains 266 objects and multiple retained build/route generations. `/.DS_Store` returns 200; the bucket also contains `images/.DS_Store` and `.gitkeep` files. A retained public source map contains one Next.js polyfill source, **not an application credential**. `collective.html` is an older page without TeamDryBox branding; `collective/index.html` has current branding. This establishes hygiene/drift, not private application-source disclosure.

The committed `next.config.js` does not define a static export and coexists with CareerOS server actions/auth. No checked-in AWS deployment workflow or infrastructure definition establishes how this commit becomes the public static release. The local ignored `out/index.html` differs from production and is not release provenance. Generated Playwright output is tracked despite ignore rules.

**Remediation and acceptance:**

- Check in a reproducible public-site build/release boundary excluding CareerOS runtime code and secrets; bind a clean release artifact and manifest to the reviewed source commit/hash.
- Scan and publish from an explicit allowlist. Reject `.DS_Store`, `.git`, environment files, unnecessary maps, generated reports, and unintended routes. Existing ignore rules alone do not remove already tracked/published files.
- Preserve an immutable rollback release. Remove obsolete bucket objects only after reviewing active-client/cache retention; deleting old chunks indiscriminately can break open sessions.
- Preserve directory/trailing-slash routes and collective/company branding. Define CloudFront/S3 configuration in reviewable infrastructure or an explicit documented change process.
- Use short-lived scoped deployment identity credentials and verify release access; IAM inspection remains GAP-01.

## SEC-07 — Establish versioned origin recovery

**Evidence:** `GetBucketVersioning` returns no versioning status: the origin bucket is unversioned. No lifecycle or replication configuration is present. Replication is not inherently required for this static site. External backup coverage was not established; absence of object-version recovery is the confirmed gap.

**Remediation and acceptance:** Enable suitable versioning or document an equivalent tested immutable release/restore mechanism. Preserve a known-good release tied to a commit; document recovery ownership/time expectations. Define noncurrent-version retention to control cost and prove a restore in nonproduction, including access controls, edge caching, assets, routes, and branding. Versioning is a recovery aid, not a complete backup or protection against every privileged deletion.

[AWS S3 Versioning documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html).

## SEC-08 — Constrain MDX filesystem paths before server exposure

**Evidence:** `lib/content.ts` joins unchecked slugs into filesystem paths. Local reproduction using `getContentBySlug('chapters', '../../ARCHITECTURE')` successfully read the existing public ARCHITECTURE.md outside content/chapters. Both dynamic content routes pass slugs to the helper and do not disable unknown dynamic params.

This is a **confirmed helper-level path-confinement failure**. HTTP route exploitation was not established. The public S3 static site cannot perform these filesystem reads. Reads are suffix-limited to `.md`/`.mdx`; arbitrary-file reads or code execution were not established. MDX itself must remain trusted, repository-controlled executable content.

**Remediation and acceptance:** Resolve slugs using an exact allowlist of published content and enforce resolved-path containment. Reject separators/traversal after decoding and unknown slugs; disable unknown dynamic params where appropriate. If draft support remains, exclude drafts from static generation and direct access, not merely index listings. Add regression tests for valid/unknown slugs, traversal variants, and drafts. These are prerequisites to deploying filesystem-backed content on a server.

## GAP-01 — Complete restricted control verification

The working site-specific AWS profile was denied IAM policy inspection, WAF logging configuration, CloudWatch log-delivery sources, Route53 hosted-zone discovery, and CloudTrail discovery. The existing administrative SSO token is expired and cannot refresh. These are **verification limits**, not proof the controls are absent.

Confirmed: legacy CloudFront access logging is disabled, no real-time-log association is configured, and S3 server access logging is absent. WAF CloudWatch metrics and sampled requests are enabled. CloudFront v2 delivery logs, persistent WAF logs, and CloudTrail management/data-event coverage remain unverified.

**Required follow-up with a current admin or purpose-built read-only audit session:**

- Inspect effective deployment identity policies, group/inline policies, credential age, MFA/session controls, repository/deployment trust, and least privilege. Do not infer full IAM scope from successful read calls.
- Verify durable CloudFront/WAF/CloudTrail destinations, retention, access controls, event coverage, error/security alerts and budget alerts. Generate a harmless request and confirm actual log delivery. If equivalent logs already exist, document them rather than enabling duplicate paid logging blindly.
- Inspect authoritative DNS, registrar lock/MFA/renewal and transfer protections. `www.kubackicollective.com` did not resolve during this review despite being a CloudFront alias; that alone does not establish a dangling-domain takeover.
- Confirm immutable backup/release coverage and a restore test. Reclassify gaps only after evidence is collected.
- If CareerOS is intentionally deployed later, separately verify live Supabase auth/rate limits, session/cache isolation, RLS enforcement with two users, and data lifecycle. No live Supabase database was queried or modified in this review.

## Controls and checks with favorable results

- HTTPS homepage certificate/hostname validation passed over TLS 1.3. Viewer policy is `TLSv1.3_2025`; TLS 1.2 was rejected by the server. The local modern client disables TLS 1.0/1.1, so those failed handshakes were not independent server-policy tests.
- HTTP apex requests redirect to HTTPS. CloudFront allows GET/HEAD only and has no additional cache behaviors. Uncredentialed CORS preflight is denied; no wildcard credentialed CORS policy was observed.
- WAF is attached with AWS managed IP reputation, common-rule, and known-bad-input groups enforcing their normal actions. This protection is bypassable through the public origin (SEC-01).
- Bucket ownership is `BucketOwnerEnforced`; ACL grants only the owner full control. Default encryption is AES256 and SSE-C is blocked. Public access is read-only in the inspected policy, not an anonymous upload grant.
- Checked `.env`, `.env.local`, `.git/config`, package manifests, and generated-report paths did not expose their files. Missing paths often return homepage HTML with a 404 status; status/body checks were both used. This is a bounded check, not proof that every possible secret path is safe.
- All ten source maps adjacent to scripts referenced by the homepage returned 404. A separate retained polyfill map exists (SEC-06); therefore the correct conclusion is not “no source maps anywhere.”
- GitHub secret scanning and push protection are enabled. The open-secret alert query returned no entries. Gitleaks reported no leaks in Git history (37 commits with scanned diffs; 39 commits reachable locally).
- Scanning all 248 published text artifacts produced one generic-key match: `paramKey` in a Next.js route tree equaling the known public slug `chapter-01-signals`. It was inspected and classified as a false positive, not a credential. No verified leaked credentials were identified.
- Source profile mutations derive `user_id` from `auth.getUser()`. Committed profile SQL enables RLS with own-user SELECT/INSERT/UPDATE predicates, including UPDATE WITH CHECK; no service-role key or security-definer bypass was found in these files. This verifies the SQL/source intent, not a deployed database's policies. [Supabase ownership-policy documentation](https://supabase.com/docs/guides/database/postgres/row-level-security).
- Existing unit tests passed: one file, three tests. `npx tsc --noEmit --incremental false` passed. Full E2E/build success is not claimed; the recorded GitHub CI failed as described in SEC-05. No dependency upgrades or security fixes were implemented by this documentation change.

## Additional conditional hardening observations

CareerOS credentials are trimmed on input, including passwords; preserve password bytes exactly. Profile validation uses `Number.isNaN` without finite/integer/range constraints and lacks explicit server-side text-size/enum limits; enforce domain constraints at both action and database boundaries if the scaffold is pursued. Raw authentication/database error messages are passed to user-visible query parameters; review information disclosure and account enumeration against actual provider behavior. The callback concatenates the request origin with `next`; use an explicit internal-path allowlist before server exposure, but no external open redirect was demonstrated here. These are scaffold observations, not confirmed production exploits.

No user-controlled HTML sink was found in the reviewed source, and present MDX content is repository-controlled. Treat future public submissions, CMS ingestion, forms, or authenticated services as a new trust boundary requiring a separate review.
